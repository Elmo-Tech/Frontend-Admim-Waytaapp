## 1. Bug Investigation & Fix

- **Scenario/selection:** investigate a hypothetical regression report that an unavailable API redirects a platform administrator to login. Select [Bug Investigation](BUG_INVESTIGATION.md), not Feature Implementation; the existing expected distinction must be preserved, not redesigned. No such failure was reproduced in Phase 3.
- **Current evidence/owner:** shared authentication composition [SessionBoundary.tsx](../../src/components/layout/SessionBoundary.tsx) calls [getPlatformSession](../../src/lib/auth/server.ts); only status 401 redirects. The [server transport](../../src/lib/api/server-fetch.ts) retains HTTP status or null for unreachable reads. [Session boundary tests](../../tests/auth/session-boundary.spec.ts) cover 401 and nonredirect null/403/500; do not claim they explicitly enumerate 503.
- **Risk/investigation:** HIGH, authentication/shared transport. Reproduce actual 401 versus 503/network/403 responses in a safe fixture, trace response mapping and caller composition, and check whether a generic alert/race produced a false report. Source currently supports the expected rule; there is no established code defect/root cause.
- **Plan/allowed scope:** no fix until a demonstrated causal path exists. If found in a future task, change only the wrong owner/branch, not all login routes or backend authorization. Extend meaningful regression coverage, preserving existing positive/negative cases.
- **Expected verification:** application baseline, session/server-fetch/transport tests, protected-child rendering, genuine logout redirect and unavailable-state rendered recovery. Mocked server results cannot prove real credentials or backend permissions.
- **Rollback/evidence gap:** revert the minimal task patch without weakening the boundary or resetting user work; document any security/availability trade-off. Reproduction/root cause Not verifiable, runtime checks Not run. **Documentation walkthrough: Passed; fix not performed.**

## 2. Performance Optimization

- **Scenario/selection:** investigate slow initial overview using [Performance Optimization](PERFORMANCE_OPTIMIZATION.md), not a speculative cache refactor. No latency measurement or bottleneck is asserted.
- **Current evidence/owner:** dashboard [OverviewPage](../../src/modules/dashboard/components/OverviewPage.tsx) performs platformServerGet('/overview'), then translates/formats aggregates and renders the shared activity feed. [server-fetch.ts](../../src/lib/api/server-fetch.ts) forwards cookie/IP and uses no-store; [existing tests](../../tests/api/server-fetch.spec.ts) protect those semantics.
- **Risk/investigation:** MEDIUM for an owner-local rendering optimization; HIGH if caching, session/transport or data-visibility semantics change. Measure comparable authenticated fixture requests: separate API/network time, server rendering/formatting and browser parse/interaction. Capture revision, dataset, locale, cold/warm conditions and repeated timing/variance before proposing code.
- **Plan/allowed scope:** identify one measured cost; preserve no-store/session/privacy rather than making data stale to manufacture a faster response. An owner-local formatting/render change needs no new runtime or infrastructure. Backend profiling or changes require separate authority.
- **Expected verification:** before/after raw timings/traces under comparable conditions, existing correctness gates, empty/error/success overview and adjacent routes. A smaller server file or faster build does not establish user latency improvement.
- **Rollback/evidence gap:** revert only the targeted optimization and remeasure if correctness/latency worsens. No baseline/post-change measurements exist from this phase; gain Not verifiable. **Documentation walkthrough: Passed; optimization not performed.**

## 4. API Contract Changes

- **Scenario/selection:** review a hypothetical proposal renaming the existing contract-write revision request field. Select [API Contract Changes](API_CONTRACT_CHANGES.md); neither the proposal nor a historical draft document supplies approval for a change.
- **Current evidence/owner:** contracts [api/contracts.ts](../../src/modules/contracts/api/contracts.ts) writeContract sends {revision, locale, text}; draft uses PUT and issue POST under the encoded subscription contract path. [use-contract-editor.ts](../../src/modules/contracts/hooks/use-contract-editor.ts) passes current revision/locale/text. [contract-editing.spec.ts](../../tests/api/contract-editing.spec.ts) checks method, encoding, body and multipart credential/boundary behavior. These are request expectations, not verified backend integration.
- **Risk/investigation:** HIGH public contract and issued-document state. Read [API conventions](../../../operations/docs/02-technical/API_CONVENTIONS.md), [classified contract reference](SPEC_MAP.md) and actual callers; compare old/new required fields, rejection/conflict behavior, issued/draft transitions, locale and unchanged text/money representation. Response fields for writeContract must be obtained from authoritative evidence, not guessed from the wrapper.
- **Plan/allowed scope:** capture approved owner/delta, old/new client-server compatibility and rollout/rollback order using the existing template. Defer implementation while the proposal lacks approval; no backend/operations change. A future frontend adaptation stays in agreed domain serialization/types/editor and relevant tests, using current transport.
- **Expected verification:** exact request/error and stale-revision cases, draft/issue/reopen behavior, loading/save failure retention/retry/repeated action and authorized real integration. Preserve multipart asset boundaries/credentials and server-composed reads. Run baseline and affected rendered/print checks; do not blindly rewrite mocked expectations to match code.
- **Rollback/evidence gap:** client rollback alone may fail against a server that removed revision; require compatible versions/transition. Approved delta, server response/error details and real integration remain Not verifiable; proposed tests Not run. **Documentation walkthrough: Passed; contracts unchanged.**

Route visits/helper tests do not establish the full flow.
- **Rollback/evidence:** preserve the first failure and isolate fixture races before fixing code; do not weaken assertions or increase timeouts as the fix. Revert only task-specific implementation/fixture changes if necessary. Node-environment Jest is not a DOM/event browser environment; no new framework is implied.
- **Gap/completion:** full save/retry/focus browser behavior and actual API sessions are Not verifiable from read-only source; no test execution in this dry run. **Documentation walkthrough: Passed; application verification Not run.**
